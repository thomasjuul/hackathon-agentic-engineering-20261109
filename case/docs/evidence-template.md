# A short record of your work

Evidence means something you actually observed: a check result, a screen, a changed file, or a real tool response. Keep a few useful notes in `docs/evidence.md` in your working copy. You do not need a long report.

## Start with these four lines

- **Task:** What were you trying to do?
- **Result:** What actually happened? What did you check?
- **Learning:** How did this session's concept help you work with Codex?
- **Next step:** What would you improve, or what help do you need?

Example: “Session 3: save the budget checkbox. I saved Fjordby and reloaded; it stayed checked. The first check failed, so Codex repaired the save code once. I accepted the change after inspecting it. Next time I would give the reload example at the start.” This is an illustration; record your own actual result.

## Add the details that apply to this session

| What to record | Keep it short |
| --- | --- |
| Goal and context | The task, files, rules, and examples you gave Codex |
| Boundaries | What Codex could change and when it had to stop |
| Agents and skills | Which ones were actually found and used; what you created or improved |
| Remote docs | Tool/server used, question, source URL, and the decision the source helped with |
| Checks | Command and working folder, expected result, observed result; passed, failed, or not run |
| Repairs and time | What failed, number of repair attempts, elapsed time, and why work stopped |
| Route through the graph | The steps actually taken; say if other routes were only discussed |
| Human decision | Accepted, requested changes, or deferred; what you inspected first |
| Supplied work | Any facilitator example or recovery checkpoint you used |
| Limitations | What remains incomplete, blocked, or untested |

## For session 4: check the app and Codex separately

**App:** Did the examples work? Can you follow an action through its response, log, and activity?

**Codex:** Did it use the right context, stay within the agreed task, report results accurately, and stop as agreed?

Do not turn expected behavior into a claimed observation. A source page explains how something should work; an actual test or app action helps show whether your implementation works. Keep credentials and real confidential information out of these notes.
